## HIGH: real defects, reproduced

**H1. The scoreboard snapshot is unauthenticated authority.** `_write_snapshot`
deliberately writes `index/scoreboard.json` without a lock, and `_load_snapshot`
trusts it after checking only the schema version. Anyone who can write the
bucket prefix can set a future `through_day` with fabricated totals and the UI
will display them, with no Object Lock trail, while the ledger short-circuits.
The ledger is tamper-evident; its cache is not, and the cache wins.

**H2. Readiness can report ready while reads are failing.** `/readyz` does one
listing plus `library.scan()`. On a cache hit `scan()` returns early, so
`last_scan_unreadable` stays empty from the last good scan and the probe returns
200 for the whole cache window even as every GET fails. That is the exact shape
of the Class B outage, which is what the probe was added to catch.

**H3. Cross-instance staleness can cause a duplicate paid generation.** The
projection cache is per process and `invalidate()` only clears the local one.
An instance that generated an asset does not tell any other instance, so for up
to 120 seconds a second instance can answer the same prompt from a library
that does not contain it yet, and pay to generate it again. That is the one
outcome the product exists to prevent.

## Second re-judge, same day: 35.0/40

Four findings. All reproduced before acting.

**The regression I wrote did not exercise the control it was named for.** The
forged-snapshot test used `through_day` 29991231, and a snapshot covering a day
that has not finished is rejected before the signature is ever compared. So the
test passed identically with the HMAC check deleted, which I proved by deleting
it. A believable forgery is backdated, and the replacement names a day that
really has finished so every cheap structural check passes and only the
signature stands between an invented total and the page. Canary verified: with
the check disabled the page shows 1000 reuses, with it enabled it shows 2.

This is the exact defect class this repo has spent a week finding in other
places. Writing the check is not the work; watching it fail is.

**The signature key was derived from the bucket credential.** It reused
`_accept_secret()`, which falls back to a digest of `B2_APP_KEY`. The attacker
the signature exists to stop is the one who can write the bucket prefix, and
that is the holder of `B2_APP_KEY`, so the key that lets them forge was the key
that lets them sign. A signature the attacker can produce is decoration. The
snapshot now reads its own `REPRISE_SCOREBOARD_SECRET`, and unset means no
snapshot is written or trusted rather than a silent fall back to a key the
attacker already holds.

**Cold path measured, and it is worse than reported.** Five sequential homepage
requests: 17.1s, then 0.32s, 0.29s, 0.20s, 0.20s. The first request to a cold
instance pays the full library projection, one listing plus a read per manifest
and per sidecar, in sequence. A judge who arrives on a cold instance waits
seventeen seconds or gives up.

**Cross-instance duplicate generation stands.** Unfixed, and now confirmed by
two reviewers. The projection cache is per process, so a second instance can
answer from a library that does not yet contain what the first just generated,
and pay to make it again.

The last two share a cause and a fix: the projection is rebuilt per process from
raw objects. A persisted index in B2, plus a version marker instances check
before trusting a local projection, collapses cold start to roughly one read and
lets a peer notice a write. That is a hot path change to a submitted entry, so
it is the operator's call, not mine.

**Public artifacts still needing an operator.** The technical brief published on
Google Drive is a stale copy: 93 tests, the old ledger path, and the retracted
no-cache claim. The repo copy is current. Devpost captions still carry the
literal `>`.
